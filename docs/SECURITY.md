# Аудит безопасности

Ревизия кода на пригодность к продакшену: скрытые баги, гонки состояний,
OWASP Top 10 (2021), CWE Top 25 и OWASP Top 10 для LLM-приложений.

Как перепроверить:

```bash
uv run --frozen ruff check .                                  # включает flake8-bandit (S)
uv run --frozen bandit -c pyproject.toml -r src/ main.py docker/
uv run --frozen pip-audit -r requirements.txt --desc          # CVE в зависимостях
xvfb-run -a uv run --frozen pytest tests/ --cov=src
```

Модель угроз: бот доступен только операторам из allow-list. Значит основной
нарушитель — **не аноним из интернета**, а скомпрометированный или
любопытствующий клиент оператора и **содержимое присланного файла**. Ниже
это учитывается в оценках.

## Исправлено

### S-1. Обход пути в `show_log` → чтение любого `.json` в контейнере
`CWE-22` · `OWASP A01` · **высокая**

`callback.data` подставлялся в путь как есть. Telegram-клиент может слать
любой callback-payload, не только тот, что нарисован на нашей клавиатуре:

```
order:log:x/../../../../catalog   ->  /catalog.json
order:log:../../../../../etc/hostname  ->  /etc/hostname.json
```

Файл затем уходил отправителю документом. Укладывается в лимит 64 байта на
callback_data — проверено, не теоретическая.

**Фикс:** `order_id` проверяется регуляркой `^[0-9A-F]{8}$` (формат, которым
мы его сами и выпускаем) и обязан существовать в БД нарядов.
Регресс-тесты: `tests/test_orders_handlers.py::test_show_log_refuses_path_traversal`.

### S-2. Доступ к чужому наряду по идентификатору
`CWE-639` · `OWASP A01` · **средняя**

`show_log` не проверял владельца. Идентификатор — 8 hex-символов, а в логе
лежат ФИО покойного, заказчика, кладбище и все суммы. Любой оператор мог
вытащить наряд другого оператора.

**Фикс:** сверка `record.chat_id` с чатом запроса.

### S-3. Непроверенное число из callback_data
`CWE-20`, `CWE-1284` · `OWASP A03` · **средняя**

`int(callback.data.removeprefix(...))` принимал что угодно. `order:addr:999999999`
умножалось на количество персонала и уезжало в позиции наряда; отрицательное
молча отключало надбавку за доп. точки.

**Фикс:** принимаются только значения, которые реально рисует клавиатура
(0…7).

### S-4. Тип файла брался со слов клиента
`CWE-434` · `OWASP A04`, `A08` · **средняя**, в связке с S-5 — **высокая**

`mime_type` задаёт отправляющий клиент. Достаточно было пометить любой файл
как `image/png`, чтобы он лёг на диск и ушёл в Pillow / PyMuPDF — парсеры на
C, то есть ровно туда, где битый файл превращается в проблему с памятью.

**Фикс:** после загрузки проверяются magic bytes; всё, что не JPEG/PNG/PDF,
удаляется до того, как попадёт к парсеру.

### S-5. 13 CVE в Pillow 12.2.0
`CWE-1395` · `OWASP A06` · **высокая**

Pillow обрабатывает именно те файлы, которые присылает пользователь. Все 13
закрыты в 12.3.0.

**Фикс:** подняли до 12.3.0; `pip-audit` добавлен в CI, чтобы следующая
партия advisory не проехала молча.

### S-6. Размер файла не проверялся, если Telegram его не сообщил
`CWE-400`, `CWE-770` · `OWASP A04` · **средняя**

`if doc.file_size and doc.file_size > max_bytes` — при отсутствующем
`file_size` (поле необязательное) проверка пропускалась целиком, то есть
запись на том шла без ограничения.

**Фикс:** размер проверяется по факту записанных байт; пустой файл тоже
отклоняется.

### S-7. Нет потолка на число файлов в наряде
`CWE-770` · `OWASP A04` · **низкая**

Каждый файл пишется на диск и потом уходит в Gemini. Зациклившаяся
отправка забивала том и жгла квоту без естественной точки остановки.

**Фикс:** `MAX_PHOTOS_PER_ORDER = 30`.

### S-8. Grafana с паролем `admin` на опубликованном порту
`CWE-1392`, `CWE-16` · `OWASP A05`, `A07` · **высокая при деплое наружу**

`GF_SECURITY_ADMIN_PASSWORD: ${GRAFANA_ADMIN_PASSWORD:-admin}` плюс
`"3000:3000"` на все интерфейсы: не заполнил `.env` — получил admin/admin в
интернете.

**Фикс:** дефолт убран, compose падает с внятным сообщением; порт по
умолчанию слушает `127.0.0.1`.

### S-9. noVNC с живым экраном 1С на всех интерфейсах
`CWE-306` · `OWASP A01`, `A05` · **высокая при `DEBUG_VNC=true`**

Порт 6080 публиковался безусловно. При включённом отладочном режиме это
трансляция сессии RDP — окна 1С с персональными данными — без какой-либо
аутентификации (ни x11vnc, ни noVNC её по умолчанию не делают).

**Фикс:** по умолчанию `127.0.0.1`, доступ через SSH-туннель; открыть шире
можно только осознанно через `VNC_BIND`.

### S-10. Секреты в логах, уходящих в Telegram
`CWE-532` · `OWASP A09` · **низкая** (утечки не подтверждено, сделано на
опережение)

`TelegramQueueHandler` пересылает записи WARNING+ в админ-чат, то есть за
пределы машины в стороннний сервис с хранением. Подтверждённой утечки нет —
проверено, что aiogram не кладёт токен в текст `TelegramNetworkError`. Но
цена ошибки здесь выше обычной.

**Фикс:** фильтр маскирует токены Telegram, ключи `AIza…` и пары
`KEY=value` во всех трёх обработчиках сразу.

## Проверено, проблем не найдено

| Область | Вывод |
|---|---|
| SQL-инъекции (`CWE-89`, `A03`) | Все запросы параметризованы, f-строк в SQL нет |
| Секреты в коде (`CWE-798`, `A02`) | `SecretStr`, значение разворачивается только в точке использования |
| Пароль RDP (`CWE-214`) | Уходит в `xfreerdp3` через stdin (`/from-stdin`), не в argv — не виден в `ps` |
| Инъекция команд (`CWE-78`, `A03`) | `shell=True` нигде нет, argv фиксированные списки |
| Обход пути при загрузке (`CWE-22`) | Имя файла от отправителя не используется: всегда `uuid4` + расширение из allow-list |
| XSS/инъекция разметки (`CWE-79`) | Весь текст из бланка экранируется; закреплено property-тестом |
| Гонки на вводе в 1С (`CWE-362`) | Единый `onec_entry_lock` + повторная проверка статуса **после** захвата: двойной тап и одновременные ✅/❌ не могут ни ввести наряд дважды, ни откатить `ENTERED` в `CANCELLED` |
| Гонки на черновике | `chat_locks[chat_id]` вокруг read-modify-write в FSM: альбом из нескольких фото не теряет кадры |
| Гонки в БД | SQLite в WAL, запись через `set_status` идёт под тем же 1С-локом |
| Рост памяти от анонимов (`CWE-770`) | `AccessControlMiddleware` зарегистрирован **до** `ThrottlingMiddleware` и возвращает `None` — неавторизованные не создают записей ни в `_last_seen`, ни в `chat_locks` |
| Контейнер (`A05`) | Не root (UID 1000), `tini` как PID 1, лимиты памяти/CPU выставлены |
| Прометей `/metrics` | Порт не публикуется на хост, скрейпится внутри compose-сети |
| Целостность зависимостей (`A08`) | `uv.lock` фиксирует версии и хеши; образ и CI ставят из него |

## Принятые риски и остаточные пункты

1. **Prompt injection в бланке** (`OWASP LLM01`). Распознанный текст
   подставляется в промпт Агента-2. Специально составленный бланк может
   попытаться повлиять на нормализацию названий. Ущерб ограничен: после
   Gemini идут детерминированные правила, Pydantic-валидация и ручное
   подтверждение оператором, а несопоставленные позиции блокируют
   автоввод. Отдельной защиты нет — принято осознанно.

2. **`/metrics` без аутентификации.** Безопасно, пока порт не опубликован.
   Если публиковать — ставить reverse-proxy с авторизацией.

3. **`data/incoming` не чистится.** Файлы отменённых и упавших нарядов
   остаются на диске намеренно (аудит), но без ограничения по времени. Это
   вопрос политики хранения — заодно и персональных данных: нужен retention
   и удаление. Не реализовано.

4. **Нет лимита расхода Gemini на оператора** сверх троттлинга в 0.7 с.

5. **Персональные данные.** В `data/` лежат ФИО, адреса и телефоны в
   открытом виде (SQLite + JSON-логи + фото бланков). Диск хоста стоит
   шифровать, доступ к `./data` — ограничивать.

## Что осталось непокрытым тестами

Общее покрытие **91 %**. Ниже среднего:

| Модуль | Покрытие | Почему |
|---|---|---|
| `telegram_bot/bot.py` | 58 % | Сборка диспетчера и цикл polling — нужен живой Telegram |
| `gemini_client.py` | 67 % | Фабрика клиента, требует настоящий ключ |
| `agent_vision.py` | 79 % | Ветки обработки ответа Gemini на реальных изображениях |
| `agent_booked_ocr.py` | 80 % | Скриншот экрана RDP |

Все четыре — граница с внешним миром (сеть, экран, API). Логика, которая
считает деньги и решает, что уйдёт в 1С, покрыта на 94–100 %.
